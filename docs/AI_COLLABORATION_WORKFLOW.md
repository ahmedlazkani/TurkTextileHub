# سير العمل المعتمد: الذكاء الاصطناعي، GitHub، وDevOps

## المبدأ

> للذكاء الاصطناعي صلاحية تطوير الكود داخل GitHub فقط. لا يملك صلاحية النشر على خادم الشركة، أو الدخول عبر SSH، أو الاطلاع على ملف `.env`، أو الوصول إلى secrets manager، أو تعديل DNS وTLS وDocker registry.

هذا الفصل بين الصلاحيات يحمي مفاتيح الإنتاج ويضمن أن كل تغيير يمر عبر مراجعة يمكن تتبعها قبل أن يصل إلى العملاء.

## توزيع المسؤوليات

| الدور | الصلاحيات | المسؤوليات | ممنوع عليه |
|---|---|---|---|
| مالك المنتج | اعتماد الأولويات والميزات | توضيح المطلوب، قبول النتيجة، اختيار وقت الإصدار | مشاركة الأسرار في التذاكر أو المحادثات. |
| الذكاء الاصطناعي / المطور | GitHub فقط | تحليل الطلب، تعديل الكود، اختبارات، وثائق، Pull Request أو commit واضح | SSH، `docker compose up` على خادم الشركة، secrets، تغيير DNS أو TLS. |
| DevOps (متيني أو البديل المعتمد) | بيئة الشركة وCI/CD | مراجعة النشر، بناء الصورة، إدارة `.env` وsecrets، النسخ الاحتياطي، المراقبة، rollback | دمج تغييرات غير مراجعة أو نشر أسرار في Git. |
| QA / حسام | حسابات اختبار | تجربة السيناريوهات، توثيق النتائج بلقطات وتوقيت دقيق | النشر المباشر أو مشاركة أسرار. |

## دورة إضافة ميزة أو إصلاح

1. يفتح مالك المنتج أو QA طلباً واضحاً يتضمن السلوك المتوقع وخطوات إعادة الإنتاج إن كان خطأ.
2. يطوّر الذكاء الاصطناعي التغيير في فرع مخصص، مثل `fix/color-image-ownership` أو `feat/product-dimensions`.
3. يضيف اختبارات عدم ارتداد وتحديثاً للوثائق عندما تتغير البيئة أو عقد API أو سلوك المستخدم.
4. ينشئ Pull Request يحتوي: ملخصاً، النطاق، الاختبارات المنفذة، مخاطر النقل، وخطة rollback إن وجدت.
5. يراجع DevOps أو مراجع كود معتمد الـ PR، ويتأكد أن لا أسرار أو ملفات تشغيلية دخلت التغيير.
6. يدمج DevOps التغيير في `master` بعد الاعتماد.
7. يبني DevOps نسخة image موقعة/موسومة من commit محدد وينشرها على بيئة staging ثم production وفق إجراء الشركة.
8. ينفذ QA smoke test، ويوثق commit/image tag ونتيجة الاختبار.

## قواعد GitHub

| القاعدة | التطبيق المطلوب |
|---|---|
| المستودع | يفضّل نقله إلى GitHub Organization الخاصة بالشركة وجعله Private. |
| الفرع المحمي | حماية `master`: منع force push، واشتراط Pull Request ومراجعة واحدة على الأقل قبل الدمج. |
| الوصول | يمنح الذكاء الاصطناعي/المطور أقل صلاحية لازمة إلى المستودع فقط؛ لا صلاحية على infrastructure. |
| الأسرار | تفعيل GitHub secret scanning وpush protection، مع عدم استخدام GitHub Actions secrets في النشر إلا إن قررت DevOps إنشاء pipeline منفصل. |
| الإصدارات | توسم كل نسخة إنتاجية بـ Git tag أو image digest مرتبط بـ commit محدد. |

## قواعد الأمن والأسرار

لا يحتوي GitHub على `.env` أو tokens أو مفاتيح KAYISOFT أو Telegram أو AI. يحتفظ DevOps بالقيم في secret manager الشركة أو ملف `.env` محمي على الخادم. يجب تدوير أي secret ظهر في logs أو screenshots أو سجل Git سابقاً قبل النقل النهائي.

عند الحاجة لتشخيص الإنتاج، يرسل DevOps **أسماء المتغيرات أو حالة وجودها فقط**، ولا يرسل قيمها. تمنع logs المعتمدة طباعة tokens أو كامل متغيرات البيئة.

## إجراءات الطوارئ

| الحالة | الإجراء |
|---|---|
| ظهور secret في log أو لقطة | يدوّر DevOps الـ secret فوراً، يحدّث secret manager، ثم يعيد تشغيل الخدمة. |
| فشل deployment | يبقى الإصدار السابق، ويجمع DevOps Build/Deploy logs بعد تنقيح أي قيم حساسة. |
| خلل بعد النشر | يوقف DevOps الإصدار الجديد أو يعيد image/commit السابق؛ لا تشغّل نسختين من Telegram polling في الوقت نفسه. |
| مشكلة منتج أو صورة | يوثق QA خطوات الإدخال، الوقت، واللقطة. يطوّر الذكاء الاصطناعي إصلاحاً في فرع منفصل ثم يمر بالدورة نفسها. |

## قالب طلب تغيير مختصر

```text
العنوان: [Bug/Fix/Feature] وصف قصير
البيئة: staging أو production
السلوك الحالي:
السلوك المطلوب:
خطوات إعادة الإنتاج:
الأثر على المستخدم:
لقطات/سجلات منزوعة الأسرار:
معيار القبول:
```

## قالب Pull Request

```text
الملخص:
النطاق والملفات المتأثرة:
الاختبارات المنفذة:
تغييرات البيئة المطلوبة (أسماء فقط):
خطة النشر لدى DevOps:
خطة rollback:
مخاطر أو قيود معروفة:
```
